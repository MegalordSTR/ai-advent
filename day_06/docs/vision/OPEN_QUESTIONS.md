## 🎮 Геймплей и баланс

### Высокий приоритет

#### 1. Баланс характеристик

**Вопрос:** Как точно должны влиять характеристики на боевые параметры?
**Контекст:** В D&D 3.5 модификатор = (характеристика - 10) / 2, округление вниз. Используем эту формулу?
**Варианты:**

1. Точно по D&D 3.5: модификатор = floor((stat - 10) / 2)
2. Упрощённо: модификатор = (stat - 10) / 2 с округлением по математическим правилам
3. Кастомная: например, линейная шкала (12 = +1, 14 = +2 и т.д.)

**Гипотеза:** Использовать упрощённую формулу с округлением в меньшую сторону для сохранения духа D&D.

#### 2. Прогрессия сложности

**Вопрос:** Как должны расти параметры врагов от уровня к уровню?
**Контекст:** Нужна формула/таблица для ХП, урона, AC врагов в зависимости от уровня подземелья.
**Данные для MVP:**

- Уровень 1: Гоблин (ХП: 10, Урон: 1d6, AC: 13)
- Уровень 2: ???
- Уровень 3: ???

**Гипотеза:** Использовать линейный рост: ХП врага = 8 + (уровень * 4), Урон = 1d6 + уровень, AC = 11 + уровень.

#### 3. Система опыта

**Вопрос:** Как рассчитывать опыт за победу над врагами и пороги уровней?
**Контекст:** В D&D сложные таблицы. Нужна упрощённая, но сбалансированная система.
**Варианты:**

1. Фиксированный опыт за тип врага
2. Опыт, основанный на "сложности" врага (ХП+урон+AC)
3. Пропорциональный уровню игрока

**Гипотеза:** Фиксированные значения: Гоблин = 25 XP, Скелет = 30 XP, Крыса = 10 XP. Порог 1→2 уровня: 100 XP.

### Средний приоритет

#### 4. Переосмысление черт (feats)

**Вопрос:** Какие именно черты из D&D 3.5 будем переосмыслять и как они будут работать?
**Контекст:** В MVP черт нет, но в V1 нужны. Примеры: "Уворот" (Dodge), "Силовая атака" (Power Attack), "Меткость" (Precise Shot).
**Проблема:** Нужен дизайн 5-7 базовых черт, которые будут значимыми, но не нарушат баланс.

**Гипотеза:** Взять 3 черты для воина, 2 для мага, 2 для паладина. Каждая даёт уникальный бонус/способность.

#### 5. Механика "Второго дыхания" (воин)

**Вопрос:** Как именно должно работать восстановление ХП?
**Варианты:**

1. Восстановление 50% максимального ХП 1 раз в день
2. Восстановление фиксированного количества (например, 20 ХП)
3. Восстановление на основе уровня (уровень * 5)

**Гипотеза:** Вариант 1 (50% макс. ХП) — сильный, но ограниченный раз в день.

#### 6. Система маны/слотов заклинаний

**Вопрос:** Как магам ограничивать использование заклинаний?
**Контекст:** В D&D слоты по уровням заклинаний. Упрощать до общей "маны" или оставить слоты?
**Варианты:**

1. Система слотов: 3 слота 1-го уровня на старте
2. Система маны: общий пул, заклинания стоят разное количество
3. КД (cooldown): каждое заклинание на перезарядке

**Гипотеза:** Система слотов (вариант 1) — проще для реализации и ближе к D&D.

### Низкий приоритет

#### 7. Долгосрочный баланс мультиклассовости

**Вопрос:** Если добавим мультиклассовость позже, как её сбалансировать?
**Контекст:** В D&D 3.5 есть сложные правила. Нужна упрощённая версия.
**Гипотеза:** Разрешить брать уровни другого класса, но с ограничением (не более 2 классов, потеря некоторых способностей).

## 🗺️ Генерация уровней

### Высокий приоритет

#### 8. Параметры клеточных автоматов

**Вопрос:** Какие конкретно параметры использовать для генерации пещер?
**Контекст:** Алгоритм требует начального заполнения, правил рождения/смерти клеток, итераций.
**Параметры для настройки:**

- Начальное заполнение (например, 45%)
- Правило рождения: минимум соседей для рождения клетки
- Правило смерти: максимум соседей для смерти клетки
- Количество итераций сглаживания

**Гипотеза:** Стандартные параметры для пещер: заполнение 45%, рождение при ≥4 соседях, смерть при ≤3 соседях, 5 итераций.

#### 9. Размещение игровых объектов

**Вопрос:** Как гарантировать корректное размещение врагов, сундуков, выхода?
**Проблема:** Нужны алгоритмы, которые размещают объекты только на проходимых клетках, не друг на друге.
**Варианты:**

1. Случайная выборка из списка проходимых клеток
2. Размещение в "комнатах" (если алгоритм создаёт комнаты)
3. Зонирование: враги в одних зонах, сундуки в других

**Гипотеза:** После генерации карты собираем список всех проходимых клеток, случайно выбираем N для врагов, M для сундуков, 1 для выхода.

#### 10. Гарантия проходимости

**Вопрос:** Как гарантировать, что сгенерированный уровень проходим от старта до выхода?
**Проблема:** Клеточные автоматы могут создавать изолированные области.
**Варианты решения:**

1. Пост-обработка: поиск и соединение изолированных областей
2. Flood fill проверка после генерации, перегенерация при неудаче
3. Использование алгоритма, гарантирующего связность

**Гипотеза:** Flood fill проверка: если не все проходимые клетки достижимы от старта, добавляем туннели между областями.

### Средний приоритет

#### 11. Разнообразие уровней

**Вопрос:** Как обеспечить разнообразие между генерациями, чтобы уровни не выглядели одинаково?
**Проблема:** Простые клеточные автоматы могут давать похожие структуры.
**Идеи:**

1. Варьировать параметры алгоритма (заполнение, правила)
2. Добавить разные "биомы" (пещеры, руины) с разными параметрами
3. Пост-обработка: добавление специальных структур (реки лавы, озёра)

**Гипотеза:** Для MVP — варьирование параметров (заполнение 40-50%, правила случайно из набора). Для V1+ — разные биомы.

#### 12. Размещение стартовой точки

**Вопрос:** Где размещать игрока на уровне?
**Критерии:** Должна быть безопасная зона (без врагов рядом), проходимая, не в тупике.
**Гипотеза:** Найти самую большую связную область, разместить в её центре или в клетке с максимальным расстоянием до стен.

### Низкий приоритет

#### 13. Тематические уровни (V1+)

**Вопрос:** Как реализовать разные тематики (пещеры, руины, подземелья)?
**Проблема:** Нужны разные тайлсеты, правила генерации, наборы врагов.
**Гипотеза:** Для каждой темы — свой набор параметров генерации, тайлсет (символы/цвета), тематические враги и предметы.

## 🖥️ Техническая реализация

### Высокий приоритет

#### 14. Архитектура Lua-модификаций

**Вопрос:** Какой именно API предоставить моддерам?
**Контекст:** Нужно решить, к каким системам будет доступ из Lua.
**Варианты:**

1. Минимальный: загрузка JSON-конфигов через Lua
2. Средний: API для изменения параметров генерации, врагов, предметов
3. Полный: доступ к игровым объектам, возможность добавлять новые механики

**Гипотеза:** Начать со среднего варианта: API для изменения существующих параметров. Расширять по мере необходимости.

#### 15. Формат сохранений

**Вопрос:** Какие именно данные сериализовать в JSON?
**Проблема:** Нужно сохранять состояние всей игры: карта, позиции всех объектов, инвентарь, прогресс.
**Риск:** Сохранения могут стать большими (карта 60x30 = 1800 клеток, каждая с данными).

**Гипотеза:** Сохранять:

- Параметры генерации уровня (семя, параметры алгоритма)
- Состояние персонажа (все характеристики, инвентарь, позиция)
- Только изменённые клетки карты (для экономии места)

### Средний приоритет

#### 16. Оптимизация рендеринга

**Вопрос:** SadConsole рендерит всю консоль каждый кадр. Как оптимизировать?
**Проблема:** 60x30 = 1800 символов, каждый с цветами — может быть нагрузкой.
**Идеи:**

1. Рендерить только изменившиеся клетки
2. Использовать слои (статический фон + динамические объекты)
3. Кэширование отрендеренных участков

**Гипотеза:** Начать с наивного рендеринга, оптимизировать при проблемах с производительностью.

#### 17. Управление памятью для процедурной генерации

**Вопрос:** Как управлять памятью при генерации больших уровней?
**Контекст:** Клеточные автоматы могут требовать несколько проходов по карте.
**Гипотеза:** Использовать одномерные массивы для хранения клеток, избегать аллокаций в цикле генерации.

### Низкий приоритет

#### 18. Поддержка разных разрешений

**Вопрос:** Как игра должна вести себя на экранах с разным разрешением?
**Проблема:** Фиксированный размер 60x30 может быть слишком мал/велик.
**Варианты:**

1. Фиксированное разрешение, масштабирование
2. Динамический размер консоли в зависимости от разрешения
3. Прокручиваемая карта для больших уровней

**Гипотеза:** Для MVP — фиксированное разрешение с масштабированием. Для V1+ — настройка размера консоли.

## 🎨 Интерфейс и UX

### Высокий приоритет

#### 19. Цветовая схема и доступность

**Вопрос:** Какие конкретно цвета использовать для разных элементов?
**Критерии:** Высокая контрастность, различимость для людей с дальтонизмом.
**Предложение:**

- Стены: белый `#FFFFFF` на тёмно-сером `#333333`
- Пол: светло-серый `#AAAAAA` на чёрном `#000000`
- Игрок: зелёный `#00FF00`
- Враги: красный `#FF0000` (гоблины), синий `#0000FF` (скелеты)
- Предметы: жёлтый `#FFFF00`

**Гипотеза:** Использовать палитру из 8-16 цветов, проверить контрастность инструментами.

#### 20. Отображение информации в панелях

**Вопрос:** Какую именно информацию показывать в панели статуса?
**Баланс:** Нужно показать важное, но не перегрузить.
**Предложение для MVP:**

- ХП: `HP: 24/30`
- Уровень: `LVL: 2`
- Опыт: `XP: 85/100`
- AC: `AC: 16`
- Глубина: `Floor: 1`

**Гипотеза:** Показать эти 5 показателей. Добавить tooltips при наведении мыши.

### Средний приоритет

#### 21. Система подсказок и обучения

**Вопрос:** Как обучать новичка без отдельного туториала?
**Идеи:**

1. Контекстные подсказки при первом использовании действия
2. Журнал событий с подсказками
3. "Советы" при смерти

**Гипотеза:** Контекстные подсказки: при первом входе в игру показать основные клавиши на экране.

#### 22. Управление мышью vs клавиатура

**Вопрос:** Как обеспечить равноправную поддержку обоих методов ввода?
**Проблема:** Некоторые действия удобнее мышью (выбор цели), другие — клавиатурой (движение).
**Гипотеза:** Полная поддержка обоих методов: движение WASD/стрелки, выбор цели мышью, контекстное меню по правому клику.

### Низкий приоритет

#### 23. Звуковое оформление

**Вопрос:** Нужны ли звуки в ASCII-игре?
**Контекст:** Звук может усилить атмосферу, но не обязателен.
**Гипотеза:** Добавить минимальные звуки в V1: шаги, удары, подбор предметов, фоновая музыка (опционально).

## 📊 Мета-вопросы

### Высокий приоритет

#### 24. Критерии готовности MVP

**Вопрос:** Когда MVP считается готовым для тестирования?
**Конкретные критерии:**

1. [ ] Игрок может создать персонажа
2. [ ] Сгенерировать уровень
3. [ ] Исследовать его, сражаться с врагами
4. [ ] Умереть или найти выход
5. [ ] Сохранить/загрузить игру
6. [ ] Нет критических багов (краши, зависания)

**Гипотеза:** MVP готов, когда все 6 критериев выполнены и игра стабильна 30+ минут.

#### 25. Стратегия тестирования

**Вопрос:** Кто, как и что тестировать?
**План:**

1. Альфа-тестирование: разработчик (функциональность)
2. Бета-тестирование: 5-10 доверенных тестеров (баланс, UX)
3. Открытое тестирование: публичный релиз MVP (масштабное тестирование)

**Гипотеза:** Использовать GitHub Issues для багов, Discord для обратной связи.

### Средний приоритет

#### 26. Документация для моддеров

**Вопрос:** Какую документацию подготовить для Lua-модификаций?
**Минимальный набор:**

1. API Reference (доступные функции, объекты)
2. Tutorial: создание простого мода
3. Примеры модов в репозитории

**Гипотеза:** Документация в формате Markdown в репозитории, обновляемая с API.

#### 27. Лицензия проекта

**Вопрос:** Какую лицензию выбрать для кода и контента?
**Варианты:**

- Код: MIT (разрешительная)

- Моды: на усмотрение авторов

**Гипотеза:** MIT для кода, CC BY-SA 4.0 для оригинального контента.
